## 3. Keys and conventions
- IDs are STRING. `dam_id` is on every table so the row filter and ABAC policy can key on it.
- All timestamps are UTC `TIMESTAMP`. Column names: `ts_utc` for readings, `*_ts` for events.
- Elevations are in metres above the dam's `ref.dam.datum`, in `*_el_m` columns. (App aliases with `*_elev_m` exist in `ref.site` only.)
- `reading_id = sha2(sensor_id || '|' || ts_utc || '|' || source_file, 256)`, assigned in silver.
- **Lineage on every reduced row:** `calib_id`, `cal_version`, `formula_id`, `formula_version`, `recompute_batch_id`, `reduced_ts`.
- **Append-only:** `silver.reading_reduced`, `ops.alarm_transition`, `ops.exceedance*`, `audit.*`, and `rpt.engineering_commentary`.
  - A recompute **appends** new rows. The current row comes from `silver.v_reading_current`; full history with `superseded_by` comes from `silver.v_reading_lineage`.
- `qa_flag` is one of `OK | SUSPECT | BAD | MISSING`. `qa_reason` holds **comma**-joined codes (`concat_ws(",")` in bronze/silver, `",".join` in `qc.py`; v1.0 text said `;`, which was wrong) (`RANGE_LOW`, `RANGE_HIGH`, `SPIKE`, `STUCK`, `DRY`, `CHECKSUM`, `AFTER_GAP`, `NULL_VALUE`).
- `sensor_id` is a channel of `instrument_id`. For single-channel instruments the seed sets `sensor_id = instrument_id`, as the app seed already does.

## 4. Alarm contract
- Machine states: `NORMAL`, `ALERT_UNACK`, `ALERT_ACK`, `ACTION_UNACK`, `ACTION_ACK`, `CLEARED_UNACK`. Levels come from `ref.threshold.level`: 1 = ALERT, 2 = ACTION.
- Transition events: `RAISE`, `ESCALATE`, `DEESCALATE`, `CLEAR`, `RTN_UNACK`, `ACK`.
- `ops.alarm_event.event_id` is the `transition_id` of the episode's RAISE. That is the key the app uses for `dam_app.alarm_ack`.
- App ack/close lifecycle (`open → acknowledged → closed` in Lakebase `alarm_ack`): the extract job turns an `acknowledged` row into an `ACK` transition in the machine and logs it to `audit.event_log`.
  - `closed` is app-only workflow state. It has no effect on the machine.
- `ref.threshold` canonical columns (FERC canvas): `tier`, `level`, `limit_type (magnitude|rate|cyclic)`, `direction (upper|lower|abs)`, `value`, `unit`, `deadband`, `persistence_on`, `persistence_off`, `pfm_id`, `eap_level_id`, `required_actions`.
  - **App change requested:** the app seed uses `upper_limit`/`lower_limit`/`rate_limit_per_day`/`rule`/`pfm_ids`/`response_action`. Please read `direction`+`value`+`limit_type`, `pfm_id`, and `required_actions` instead.
  - Rate limits are per day.
- **v1.4 no-NULL rule:** a reading-driven transition (`event` ≠ `ACK`) always has `value`, `metric_value` and `reading_id`
  (CHECK `ck_alarm_transition_value` in `sql/ddl/07_ops.sql` + evaluator pre-write guard; the engine never transitions on a
  NULL/BAD/MISSING reading). Only `ACK` rows have NULL value. `ops.alarm_episode.value` and its lineage columns come from the
  latest reading-driven transition, so they are non-NULL for every episode (an episode always starts with a RAISE on a
  reading). Tests: `tests/test_alarm_lineage_contract.py`.
- **v1.5 (QA-035, decision):** `metric_value` stays **NOT NULL** in `ck_alarm_transition_value` for every non-ACK
  transition, needed for traceability. The engine (`dam_safety.alarms`) passes the evaluated metric, `reading_id` and
  `value` on **every** non-ACK transition, including `CLEAR`, `RTN_UNACK` and `DEESCALATE` (v1.4 left them NULL, so the
  first return to normal tripped the guard and halted evaluation for every sensor). **App Developer: any manual or
  app-originated non-ACK transition must also fill `metric_value` (and `value`, `reading_id`)**, or the write fails.
- **v1.5 erroneous mark:** `ops.alarm_episode` carries `erroneous_mark` (BOOLEAN, false when unmarked),
  `erroneous_reason`, `erroneous_marked_by`, `erroneous_marked_ts`: the latest `ops.reading_erroneous_mark` row for the
  episode's `reading_id`. The app reads these instead of `ops.reading`.
- **v1.6 installation lineage (app §7 10d):** `ops.alarm_transition.installation_version TIMESTAMP` (nullable, last
  column) = `ref.incl_installation.effective_from` of the row valid at the transition's reading time
  (`batch.installation_version_at`, same half-open rule as §5.5). `alarm_evaluator` sets it for sensors whose
  `ref.sensor.instrument_id` has `ref.incl_installation` rows, NULL for other instruments and for ACK; no covering
  row or overlapping rows → NULL plus a logged issue (evaluation never halts). `ops.alarm_episode.installation_version`
  = that of the latest reading-driven transition. **UNVERIFIED / no feed yet:** the evaluator reads
  `silver.v_reading_current`; inclinometer results live in `silver.incl_reduced`, so until an inclinometer metric is
  fed to the evaluator no inclinometer alarm (and no non-NULL value) exists.
- **v1.7 `cdse_ack_required` (DSSMP; Genie 2026-11-09, App Dev agreed).** `ref.threshold.cdse_ack_required BOOLEAN NOT
  NULL DEFAULT false` (the alarm-rule table; per dam via `dam_id`, per rule `threshold_id`, versioned SCD2 with the
  rule). Source: the dam's DSSMP. TRUE = the dam's CDSE (`ref.dam.cdse_id` or a CDSE membership,
  `ref.v_dam_reviewer_authority`) must acknowledge this rule's alarms **at any level**. **Snapshot at open:**
  `ops.alarm_transition.cdse_ack_required_at_open BOOLEAN` (last column) is written by `alarm_evaluator` on the
  **RAISE** row only, from the rule version that raised (`threshold_id`, `threshold_version`, the version in effect
  at evaluation; `alarms.cdse_ack_snapshot`); NULL on every other event. The table is append-only, so the snapshot is
  immutable for the life of the episode; un-flagging the rule mid-episode does not change it
  (`tests/test_cdse_ack_required.py`). If the flag cannot be read the alarm is still raised and the snapshot is TRUE
  (conservative) with a logged issue. RAISE rows written before v1.7 stay NULL (unknown, never backfilled).
  **`ops.alarm_episode`** exposes `cdse_ack_required_at_open` (binding snapshot), `cdse_ack_required` (CURRENT flag of
  the opening rule's `is_current` version; NULL if the rule is gone), `raise_threshold_id`, `raise_threshold_version`.
  **Extract:** the `ALARM_ACK` row in `audit.event_log` carries both in `payload` (recorded, not enforced).
  **Enforcement (403 for a non-CDSE ack) is the app's** (c4a384c ORs the snapshot, the view's rule flag and the
  current `ref.threshold` row). Migration `sql/migrations/v1_7_001_cdse_ack.sql`.
- **v1.7 versioning rule (Genie decision).** `ref.threshold` is SCD2 on (`threshold_id`, `threshold_version`).
  Changing `cdse_ack_required` (or any rule field) creates a NEW version: `threshold_version` = max + 1,
  `effective_from` = the publication time (never back-dated), `set_by` = the publisher; the previous version keeps
  every rule field and only gets `effective_to` / `is_current = false`. An in-place UPDATE of a rule field is a
  contract violation. Writers use `dam_safety.threshold_publish.plan_threshold_publication` and may check with
  `assert_versions_immutable`. Audit trail: `gold.v_threshold_cdse_ack_changes` (one row per version whose flag
  differs from the previous version). Delta cannot block an UPDATE; detect one with
  `table_changes('ref.threshold', <v>)` rows of `_change_type = 'update_postimage'` whose flag changed. The app's
  go-live payload carries `cdse_ack_required` (bool, absent = false); the publisher job itself is not in this repo
  yet (VERIFICATION THRESHOLD-VERSION).

### 5.5 Inclinometers (v1.1, steering 9; app Q9)
- Storage rule: SI units, depth in metres **from top of casing, keyed to the interval top**; raw readings kept
  alongside (bronze `raw.incl_survey_raw` is append-only and never edited). Workbook "depth from bottom" labels are
  re-keyed with `top = casing − d − L` (`inclinometer.installation.rekey_from_bottom_label`) — **workbook import profile
  only** (`survey_import.import_reading(profile="workbook")`), stored with `depth_reference='from_bottom_label'` and the
  raw label in `raw_depth_label`. GTILT and DigiPro profiles keep native from-top depths (`depth_reference='top_of_casing'`).
- SAA measurand B is sign-flipped **once at ingest** (`sign_mult_B = -1` in `ref.incl_installation`, row flagged
  `sign_normalized`).
- Corrections are **never** manual cell edits: each is a `ref.incl_correction` row (columns, in order:
  `record_id, dam_id, instrument_id, survey_id, axis, correction_type, parameter_name, auto_value, detection_method,
  detection_statistic, override_value, applied, sign_convention, depth_range, reason, source_citation, user,
  timestamp_utc, before_value, after_value, software_version, input_file_sha256, superseded_by, reviewed_by, reviewed_utc` — the REPORT §6.3 audit fields
  plus review; exact list asserted by `tests/test_inclinometer_module.py`). Apply order: depth → bias → sensitivity → rotation.
  - **Rotation** (v1.2): axis A only (B UNVERIFIED); `sign_convention` required on every rotation record, one of
    `MIKKELSEN2003_EQ9` (A = A′ + sinα·B′), `GTILT_PLUS_SIN` (A = A′ − sin r·B), `A_corr=A-f*B`. Off by default: applied
    only with an independent review (`reviewed_by` ≠ `user`, `reviewed_utc`).
  - **Spiral** (v1.2): deferred. `spiral` stays a valid `correction_type`, but `applied=true` is rejected. Every survey on an
    installation with `ref.incl_installation.spiral_survey_id` set (or a spiral record) gets info code `SPIRAL_NOT_APPLIED`
    appended to `qa_reason`; `qa_flag` severity is unchanged. A checksum shift alone never creates a correction (it makes the survey SUSPECT).
  - **QA-020 between-set bias QC** (v1.2, procedure §7.1; `dam_safety.inclinometer.qc.between_set_bias_qc`, beside the
    checksum flag). Per survey × axis, against a reference set (default `baseline_survey_id`, user-overridable) over the
    stable zone (`ref.incl_installation.stable_zone_top_m`, required; NULL → bottom 5 intervals and
    `stable_zone_assumed=true`; never auto-detected). Output `BiasQC`: `suspect_flag` (|Δ mean checksum| > 10 A / 20 B;
    investigate only), `za_proposed_c` (**QA-021**, rule `QA021-v2`, procedure §5 lead rulings 2026-11-02: every Δ = suspect −
    reference; ΔD = mean(ΔA0 − ΔA180) over the stable zone; **ZA/ZB = −ΔD always, added to A0** (D′ = D + ZA); bs is never
    used for the value), evidence `n`, `mean_dD` (= ΔD), `sd` (sample SD of per-depth ΔD), `se` (SD/√n), `spread`
    (max − min, evidence only), `mean_cs_change` (bs = mean(ΔA0 + ΔA180)), `abs_dD` (|ΔD|), `abs_bs` (|Δ0+Δ180|),
    `crosscheck_diff` (||ΔD| − |bs||), `crosscheck_tol` (max(2.0, 3·SE), configurable, UNVERIFIED, ranks only),
    `crosscheck_verdict` (`AGREE` | `SUSPECT`), `requires_review` (always true), `reference_survey_id`, plus
    `stable_zone_assumed`, `params_unverified` (always true for the defaults), `rule` (`QA021-v2`), `status`
    (`NO_PROPOSAL | PROPOSED | SUSPECT_CROSSCHECK | BAD_RESURVEY`), `gates`, `qa_flag`. Gates: (i) n ≥ 5; (ii) |ΔD| > 3·SE;
    (iii) SD ≤ 8 A / 16 B — fail → `NO_PROPOSAL`; (v) |ZA| ≤ 25 else `BAD_RESURVEY` (`qa_flag=BAD`, no ZA); (iv) magnitude
    cross-check ||ΔD| − |bs|| ≤ tol → `PROPOSED` (verdict AGREE), else `SUSPECT_CROSSCHECK` (verdict SUSPECT). **Both carry
    ZA** and `qa_flag=SUSPECT`; SUSPECT is a review ranking, not a rejection. There is **no sign-agreement gate** (v1 field
    `sign_agree` removed): an A180-only bias δ gives ΔD = −δ, bs = +δ, ZA = +δ and must be PROPOSED (δ = +6 → corrected
    stable zone 0.0 mm). The QA-020 v1 `equal_opposite` 0.5 ratio is removed. **Never auto-applied:**
    `qc.bias_proposal_record` writes an `applied=false` `ref.incl_correction` row (`detection_method='between_set_bias_qc'`;
    `detection_statistic` carries `ZA`, `abs_dD`, `abs_bs`, `crosscheck_verdict`, `status`, `requires_review=True`). A bias
    row with `applied=true` must have reviewer approval per **§5.5.1** (v1.5); the engine rejects one without it (skipped,
    `CORRECTION_RECORD_INVALID`) and ignores unreviewed bias rows. All thresholds are configurable `BiasQCParams`
    (UNVERIFIED engineering judgment).
  - **Field naming (v1.5):** the contract and API field is lowercase `za` (and `zb`). The engine attribute is
    `za_proposed_c` and the stored `detection_statistic` key stays `ZA` (existing records keep parsing); the mapping is done
    once at the boundary: `qc.API_FIELD_MAP = {"ZA": "za", "ZB": "zb"}`, `qc.parse_detection_statistic()` (stored text →
    dict with `za`) and `qc.bias_qc_api()` (BiasQC → API dict). No API payload carries `ZA`. Unit: reading units
    (digits), D′ = D + za.

#### 5.5.1 Correction approval, append-only versions and the review signature (v1.5, QA-039 / QA-036)
- **Append-only.** `ref.incl_correction` has `delta.appendOnly=true`; `UPDATE`, `DELETE` and `MODIFY` are granted to
  nobody (`sql/ddl/10_security.sql` grants no write privilege; the owning runtime service principal's jobs only
  `INSERT`, and `delta.appendOnly` makes UPDATE/DELETE fail even for the owner). A change is a **new version row** whose `supersedes` names the `record_id` it
  replaces; nothing is updated in place. `superseded_by` is a legacy column (NULL in new rows); "superseded" is derived in
  `gold.incl_correction_status` (a later row's `supersedes`, or a legacy `superseded_by`).
- **Approval = an insert-only `audit.review_record` row**, the source of truth: `subject_type='incl_correction'`,
  `subject_id` = the `record_id` reviewed (the proposal), `decision='approve'` (or `reject`), `comment` = rationale
  (required, non-empty: CHECK `ck_review_record_subject_decision`), `reviewer_id`, `signed_ts`, `signature_hash`
  (below). The app writes it to Lakebase `dam_app.review_signoff`; `dam_lakebase_extract` appends it to
  `audit.review_record` (§7). Applying is then a **new `applied=true` version row** with `supersedes` = the proposal,
  `review_id` = that review, the same reviewed values, and `reviewed_by`/`reviewed_utc` as a denormalized copy.
- **An applied row counts only when** (`corrections.approval_problem`, used by `batch` / the job): its `review_id` names an
  `audit.review_record` row with `subject_type='incl_correction'`, `decision='approve'`, `subject_id` = this `record_id`
  or its `supersedes`; `reviewer_id` = `reviewed_by` and ≠ the author (`user`) of the row and of the reviewed subject
  (case-insensitive); `signature_hash` = `review_signature(review, subject as stored)`; and, when the subject is the
  proposal, the applied row carries exactly the reviewed values (`instrument_id, survey_id, axis, correction_type,
  parameter_name, auto_value, override_value, sign_convention, depth_range`). `reviewed_by`/`reviewed_utc` alone never
  approve. Otherwise the row is skipped with `CORRECTION_RECORD_INVALID`.
- **DB CHECK** `ck_incl_correction_applied_reviewed` (`sql/ddl/02`): `NOT applied OR (reviewed_by IS NOT NULL AND
  reviewed_by <> user AND reviewed_utc IS NOT NULL AND review_id IS NOT NULL)`, so an applied row without a review cannot
  be stored. The CHECK cannot see `audit.review_record`; the review row and signature are verified by the job.
- **`approval_status`** (`gold.incl_correction_status`, api_contract §4.1): `superseded` (a later version supersedes it)
  > `approved` (applied with a matching approve review) > `unreviewed_applied` > `proposed` (applied=false).
  **`unreviewed_applied` is a defensive app-only status**: the CHECK makes it impossible for rows written after v1.5, but a
  reader must still handle it (legacy rows, a review row not yet extracted) and must never show such a value as approved.
  (The app currently raises `DataIntegrityError APPLIED_WITHOUT_VALID_REVIEW` instead; either is acceptable as long as the
  value is withheld.)
- **Review signature** (`corrections.review_signature`; same rule as the app's `backend/signoff.py`). A content hash for
  tamper evidence, not a key-based signature:
  1. Payload = `{"signoff": {…}, "subject": {…}}`. `signoff` = the review row's fields `review_id, dam_id, subject_type,
     subject_id, review_level, decision, comment, reviewer_id, reviewer_pe_license, signed_ts`. `subject` = **every**
     `ref.incl_correction` column (`corrections.AUDIT_FIELDS`, 27: `record_id … reviewed_utc, supersedes, review_id`) of
     the reviewed record **as stored**. Missing keys are `null`.
  2. Each value through `canonical_value`: `None`/NaN → `null`; a timestamp (datetime, or a string `YYYY-MM-DD[T ]HH:MM…`,
     `Z` allowed) → UTC ISO-8601 with microseconds and `+00:00` (`2026-03-02T12:00:00.000000+00:00`; naive = UTC); a
     date → `YYYY-MM-DD`; a tuple range → `"lo..hi"`; anything else unchanged (numbers stay JSON numbers).
  3. Serialise with `json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False)` (keys sorted at every
     level, so field order in the lists above does not matter; no whitespace; non-ASCII kept as UTF-8).
  4. Encode UTF-8; hash **SHA-256**; store lowercase hex (64 chars) in `audit.review_record.signature_hash`.

### 7.2 Ownership of writes (v1.1, app Q11)
The app writes Lakebase only. `dam_lakebase_extract` is the **only** writer of `ALARM_ACK` rows to `audit.event_log`;
the alarm evaluator is the **only** writer of `ACK` transitions (dedup tag `lakebase_ack:<event_id>`). `certified`/`submitted`
DSSMR status is set only by the PE sign-off path (`audit.review_record`), never by the app.

### 7.3 Synced tables (v1.1, app Q12)
**Not used.** A Lakebase synced copy of `gold.instrument_latest` read by the app service principal would bypass UC row
filters. Latest values are read through the SQL warehouse on behalf of the user. `resources/app.yml` has no synced-table
block (it was removed; `tests/test_bundle_config.py::test_app_yml_has_no_synced_table_wired`).
- Lakebase is never the system of record for a regulatory record.

### 7.4 Endpoint reference (v1.5, App Developer mismatch 3)
`resources/app.yml` passes `ENDPOINT_NAME = ${resources.postgres_endpoints.dam_lakebase_primary.id}` (and branch
`.id`). The docs say `.id` resolves to the full resource name, but this is **UNVERIFIED until `databricks bundle
validate`** (and a deploy) has run (`docs/VERIFICATION.md` LB-REF). The app should treat the value as an opaque endpoint
name and fail loudly if it does not resolve.
